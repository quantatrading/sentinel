# Sentinel 0.3.15

Security changes now have a persistent reference and lifecycle:

- A newly detected change generates one warning.
- Repeated unchanged checks update its count and observed duration without hourly repeat alerts.
- `/sentinel investigate REF` shows before/after evidence and owner details.
- `/sentinel acknowledge REF` marks the change reviewed without changing the baseline.
- `/sentinel approve REF` accepts only that difference; other changes remain unapproved.
- Resolved changes retain history. A later recurrence creates a new reference.

Listener baselines now retain all observed process names, UIDs and PIDs. PID-only
restarts are excluded from baseline comparisons. Old baselines retain their saved
owner names, but missing historical PIDs cannot be reconstructed and are labelled
“PID not recorded”. Review and approve a fresh full baseline if you want to record
current PID metadata. Do not approve unexpected changes just to populate PIDs.

Changes and approvals persist across restarts and are audited. Unchanged legacy
drift counters migrate without resuming hourly warnings. New references are listed
by `/sentinel`; arbitrary references from older messages cannot be reconstructed.
Counts represent samples, not separate incidents. Duration may include downtime
or collection gaps and is not proof of uninterrupted observation.

## Upgrade

Download the archive and its checksum into the same directory:

```bash
sha256sum --check --strict sentinel-0.3.15.tar.gz.sha256
tar -xzf sentinel-0.3.15.tar.gz
cd sentinel-0.3.15
sudo ./install.sh
```

Configuration and credentials are preserved; only Sentinel restarts. Send
`/selftest` and `/sentinel` after upgrading. Keep a protected state/configuration
backup; downgrades are not guaranteed compatible. Tests cover repeat suppression,
scoped approval, acknowledgement, restart persistence, legacy migration and PID
churn. Live Telegram and target-server behaviour need verification after upgrade.
